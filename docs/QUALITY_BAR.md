# CourseAccess: measurable quality bar against professional PDF tools

Updated: 22 November 2026. These comparisons use public vendor descriptions, not direct performance testing. They are not claims of product superiority.

| Feature | CourseAccess current capabilities | External professional baseline | Objective gate |
| --- | --- | --- | --- |
| OCR / scanned PDFs | Local Tesseract OCR, word confidence, searchable visual copy | Adobe and CommonLook include scan and tagging workflows | Real scans, OCR accuracy/word error rate, pixel-equivalent output |
| In-place tagging | New tagged reading copies, not original object-level repair | Adobe Acrobat Pro reading-order/tag edits, CommonLook advanced editor | Preserve source semantics and layout; verify repaired original with PDF/UA tool |
| Tables | HTML header cells, tagged PDF Table/TR/TH/TD | axesPDF and CommonLook offer complex table correction | Merged headers, scope, spans, multi-page cells and screen-reader associations |
| Mathematics | LaTeX-to-MathML HTML, PDF Formula/Alt tags | Professional tools vary | Formula semantic fidelity, complex STEM corpus and assistive technology |
| Figures | User-approved adjacent descriptions | Vendors offer figure tagging/alt descriptions | Figure-to-content association, decorative artifacts and accuracy validation |
| Reading order | User can reorder blocks inside new reading copy | Acrobat changes original PDF page tag order | Verified logical navigation through the tag tree on multi-column documents |
| Independent PDF/UA | This PR introduces actual veraPDF CLI checks on browser exports | veraPDF validates PDF/UA-1 and PDF/UA-2 | Independent validator results and exact failures; no false pass statements |
| Privacy | Browser-local PDF processing | Cloud/desktop designs vary by vendor | Explicit authorization before any private PDF is sent to a service |

## Release quality requirements

1. Independent validator run on actual generated artifacts with exact failed rules.
2. Positive control generated by a separate PDF/UA-capable engine; validator must correctly pass it.
3. Browser end-to-end tests for OCR, searchable copies, tagged reading PDFs, accessible tables, math and reading order.
4. Unaltered source files and no surprise upload of private material.
5. Assistive-technology checks and representative academic PDFs before marketing any formal conformance.
6. A failed PDF/UA result is a product defect to prioritize, not a marketing label to hide.

The independent PDF/UA-1 sample validation gate is now strict: any generated sample failure blocks CI and production deployment. The browser-produced basic and STEM samples have passed the current veraPDF profile. This is narrower than universal PDF/UA certification: robust coverage still requires larger real-document corpora, screen-reader walkthroughs, figure semantics and tests on arbitrarily complex source documents.

## Phase 3 findings

The loaded document editor failed an initial automated axe WCAG color contrast check on desktop and mobile despite public pages passing. The Phase 3 branch adds an editor-specific regression and increases text contrast without removing the visual design. Use the latest GitHub Actions result, not the existence of this code, to establish whether the correction passes.

This change also tests Office source order and prevents silent paragraph/table clipping. It does **not** establish a certified PDF repair engine or prove native DOCX/PPTX/XLSX layout preservation.

## Runtime provider-independence improvement

Tesseract worker/core and five OCR language packs are now included as first-party static build assets. This removes a runtime requirement to access a third-party model CDN while preserving browser-local recognition. Network availability for first load and Cloudflare static delivery still matter. The build script fails if an OCR asset cannot be packaged under the Cloudflare 25 MiB/file cap. Browser regression checks are necessary but not a substitute for production load/performance benchmarking.

### Vector and Office figure limitations

The checker now inspects both PDF raster painting operations and PDF vector path construction/painting as **review prompts**. Lines, borders and decorations can generate a false-positive review reminder, while a complex figure can still escape heuristic detection. This is not image comprehension and does not infer accurate alt text. DOCX source image description metadata is copied into explicitly marked **source-provided, unverified** text for educators to review; the reading format does not pretend to reconstruct original image placement or figures.
